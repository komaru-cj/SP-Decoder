# 总体实验设计

## 1. 实验目标

当前阶段要把原来的“10 个位置单包采集后离线叠加”升级为“15 个独立 LoRa 节点同时在线、真实随机接入、真实空口碰撞”。实验要回答：

1. 在不同归一化业务负载 `G` 下，SP-Decode 对真实异步碰撞的包成功率、吞吐量和碰撞恢复能力如何。
2. 双天线联合处理相对单天线处理是否稳定提升成功率。
3. 离线叠加结果与真实射频碰撞结果有多大差异，差异来自频偏、时钟漂移、功率不平衡、前端非线性还是检测漏包。

## 2. 系统结构

```mermaid
flowchart LR
    C["控制端 Ubuntu + B210"] -->|"LoRa CONFIG / START"| N["15 x STM32F103C8T6 + SX1276"]
    N -->|"真实随机接入与空口碰撞"| R["接收端 Ubuntu + 双通道 B210"]
    R --> I["连续双通道 IQ + JSON 元数据"]
    I --> F["前端检测、同步、参数估计"]
    F --> D["单天线 / MRC / SP-Decode"]
    D --> V["PHY CRC + payload CRC + run/node/seq 校验"]
    V --> M["PRR、吞吐量、恢复率、时延和失败分类"]
```

控制端和接收端应使用两台不同的 B210。控制端只负责广播控制帧；15 个节点才是业务包发射源。接收端持续采样，不参与业务调度。

## 3. 固定物理层参数

所有控制帧和数据帧必须一致使用以下参数：

| 参数 | 值 |
|---|---:|
| 中心频率 | 487700000 Hz |
| 扩频因子 | SF10 |
| 带宽 | 125 kHz |
| 编码率 | 4/5 |
| 前导码 | 8 symbols |
| Header | Explicit |
| LoRa PHY CRC | 开启 |
| Sync word | `0x34` |
| IQ inversion | 关闭 |
| 数据 payload | 20 bytes |
| 接收采样率 | 1 MS/s，每通道 |
| 数据包理论 ToA | 370.688 ms |
| 固件整数 ToA | 371 ms |

任何一个参数不一致都可能表现为“节点不响应控制”或“接收端检测到能量但无法解码”。

## 4. 业务模型与 G

节点完成 warmup 后，先在一个平均周期内随机选择首次发送时刻，后续空闲间隔服从指数分布。设活动节点数为 `N`，单包空口时间为 `T_packet`，平均空闲间隔为 `E[T_gap]`，则：

```text
单节点占空比 d = T_packet / (T_packet + E[T_gap])
总业务负载 G = N * d
E[T_gap] = T_packet * (N / G - 1)
```

控制协议提供固定 profile：

| traffic_profile_id | G |
|---:|---:|
| 0 | 0.25 |
| 1 | 0.5 |
| 2 | 1.0 |
| 3 | 1.5 |
| 4 | 2.0 |
| 5 | 3.0 |

要求 `G < N`。例如单节点实验只能使用 `G=0.25` 或 `0.5`。15 节点按理论 ToA 计算的平均空闲间隔为：

| G | 平均空闲间隔 |
|---:|---:|
| 0.25 | 21870.592 ms |
| 0.5 | 10749.952 ms |
| 1.0 | 5189.632 ms |
| 1.5 | 3336.192 ms |
| 2.0 | 2409.472 ms |
| 3.0 | 1482.752 ms |

固件用 371 ms 整数 ToA 计算，所以 manifest 同时记录理论值和固件整数值。

## 5. 自变量、因变量与控制变量

自变量：活动节点数 `N`、业务负载 `G`、随机种子、节点空间位置、节点发射功率、接收算法（单天线、MRC、SP-Decode）。

核心因变量：

- payload CRC 正确包数与包成功率。
- 每秒成功解码包数和有效吞吐量。
- 每个节点的成功率、公平性和连续丢包长度。
- 前端检出数、后端尝试数、PHY CRC 通过数、payload CRC 通过数。
- 碰撞阶数、功率差、时间偏移、频偏与成功率之间的关系。

控制变量：频率、SF、BW、CR、前导码、sync word、payload 长度、天线位置、线缆、接收增益、采样率、节点供电方式和实验场地。

## 6. 推荐实验矩阵

先做 30 s 短 run 排错，再做 120 s 正式 run。每个正式配置至少使用 5 个不同 `run_id/global_seed/payload_seed` 重复。

| 阶段 | N | G | 目的 |
|---|---:|---|---|
| A | 1 | 0.25, 0.5 | 逐板检查、频偏/功率基线、payload 和 CRC |
| B | 2 | 0.5, 1.0, 1.5 | 验证真实双包碰撞和时间对齐 |
| C | 4 | 0.5, 1.0, 1.5, 2.0, 3.0 | 验证多用户检测与参数估计 |
| D | 15 | 0.25, 0.5, 1.0, 1.5, 2.0, 3.0 | 正式规模实验 |

节点位置不能每次随意改变。建议固定 15 个编号位置，记录节点到接收天线的大致距离，并在整个对比组中保持不变。必要时增加“功率均衡布局”和“near-far 布局”两个独立实验组。

## 7. Run 标识与可复现性

每次实验使用唯一 `run_id`。推荐编码：

```text
0xNNGGSSRR
NN = 节点数量编码
GG = G profile
SS = 场景或位置组
RR = 重复编号
```

每个 run 必须同时保存：控制 manifest、`.sc16`、`.sc16.json`、解码结果、统计摘要、现场记录。不能只保留最终图表。

## 8. 有效性门槛

以下条件全部满足才把 run 纳入正式统计：

- 控制 manifest 存在，`run_id` 与 IQ 元数据一致。
- 实际中心频率、采样率、带宽、通道数与配置一致。
- `overflow_count == 0`、`timeout_count == 0`。
- 两通道 `clipping_count == [0, 0]`，峰值不过载。
- 捕获覆盖 CONFIG、START、warmup、完整业务时段和尾部保护时间。
- 数据解码不使用 manifest 的期望发包时刻作为检测先验。
- payload 的 `run_id/node_id/sequence` 合法，且应用层 CRC16 正确。

控制端期望调度只能用于实验结束后的完整性对账，不能作为算法输入，否则会产生 oracle leakage，夸大算法性能。

## 9. 没有 USB-TTL 的影响

没有 USB-TTL 不妨碍做实验，但降低了节点侧可观测性：无法逐包读取 `TX_START/TX_DONE/TX_TIMEOUT`，无法直接确认节点是否重启，也无法测量每块板的真实调度漂移。因此：

1. 单节点阶段必须逐板验证 LED、空口包、节点 ID、序号递增和双 CRC。
2. 正式 run 用 manifest 预测“应发包”，用接收结果判断“已观测包”；两者差异标记为发送未观测，不能武断归因于解码失败。
3. 现场用视频拍摄 15 块板 LED 可作为辅助证据，但不是精确时间真值。
4. 论文中应明确该限制；若后续需要区分“节点没发”和“接收没解出”，应增加串口日志、GPIO 逻辑分析仪或独立空口监听器。
