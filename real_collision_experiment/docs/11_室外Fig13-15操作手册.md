# 室外 Fig.13--15 操作手册

本文对应室外 campaign `fig13_fig15_outdoor_sf8_sf10_sf12_bw250_d025_r6_20s`。三个图共用以下统计约束：节点业务发送 20 s；正式建库、解码和 PRR 统计只使用业务阶段完整中间 5 s，即 `[traffic_start + 7.5 s, traffic_start + 12.5 s]`。接收端每个 run 实际采集 55 s（计划 50 s 加 5 s guard），以覆盖控制帧、预热、业务期和尾部。

以下 Ubuntu 命令均在 `/home/chengjing/real_usrp_experiment` 目录执行。每条命令均写入完整绝对路径，无需设置 shell 变量。

Windows 示例假定仓库位于 `C:\real_usrp_experiment`，Python 位于 `D:\mysoft2\radioconda\python.exe`；若 Windows 仓库位置不同，只替换命令中的 `C:\real_usrp_experiment` 前缀。目录名中的 `d025` 表示 Fig.13 的 25% duty；Fig.15 已单独配置为 75%，不要根据目录名手工改回 25%。两台机器不需要联网，但必须使用同一版 `campaign.json`。

## 1. Fig.13：不同 SF、不同解码器的 PRR

### 1.1 采集设计

- 室外，BW=`250 kHz`，每节点 duty=`25%`，业务发送时长 20 s。
- SF=`8,10,12`，分别使用 PHY profile `4,5,6`。
- 现场实际采集 `N=3,6,9,12,15`，共 `3 x 5 = 15` 个 source run。
- `N=18,21,24` 不做新的现场发射。它们分别由同一 SF/BW 下的真实 `N=15` IQ 与真实 `N=3/6/9` IQ 按业务开始时刻对齐后相加得到。
- 图中每个 SF 一个分面，横轴为 `N=3,6,9,12,15,18,21,24`，比较 `SP-Decoder`、`SP+repair`、`MRC`、`CIC`、`PCube`、`MaLoRaGW` 六种解码器。

```text
PRR = CRC 有效解码的匿名物理候选数
      / 共享 v2 匿名 fine-sync 库认证的物理候选数
```

## 2. Fig.14：不同 SNR bin、不同解码器的 PRR

### 2.1 数据来源

Fig.14 不进行新的室外发射，采集数据只来自 Fig.13 的物理 SF8/BW250、`N=3` source report。合成 run、SF10 source 和其他节点数 source 都会被脚本自动排除。该 source report 必须已经按严格居中 10 s 完成解码。

脚本以源 report 对应的共享 `fine_sync_anonymous_physical_v2` 认证目标作为固定 D，在对应 IQ 切片上添加与实测双接收通道噪声协方差匹配的复高斯噪声。目标中心为 `-35,-20,0,+15 dB`，最终按实测 median preamble SNR 归入：

```text
<-30 dB
[-30,-10) dB
[-10,10) dB
>=10 dB
```

因此 Fig.14 是固定共享 fine-sync 目标上的解码 PRR，用于比较低 SNR 解码能力，不是低 SNR 条件下的端到端检测召回率。每种解码器仍使用：

```text
PRR = CRC 有效解码的匿名物理候选数 / 共享 v2 匿名 fine-sync 目标数
```

## 3. Fig.15：近远效应

### 3.1 采集设计

- 室外，SP 方案，SF12/BW250 kHz，每个活动节点 duty=`75%`，业务发送时长 20 s。
- 节点 A 为 ID 1，固定在距 gateway 80 m 处。
- 节点 B 为 ID 2，只使用 7 个距离：`20,40,60,80,100,150,200 m`。
- 每个 B 距离采两个 run：先 `ab_simultaneous`（`active_nodes=[1,2]`，A/B 各 75%，`G=1.5`），后 `b_only`（`active_nodes=[2]`，仅 B 以 75% 发射，`G=0.75`），共 `7 x 2 = 14` 个 run。
- 同一位置的两个 run 连续采集；移动到下一位置前留 30 s `POSITION_BREAK`。
- 图中三条线为：AB 同时上电时 A 的 PRR、AB 同时上电时 B 的 PRR、只有 B 上电时 B 的 PRR。
