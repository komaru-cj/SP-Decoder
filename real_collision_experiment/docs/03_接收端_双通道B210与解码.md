# 接收端：双通道 B210、前端检测与后端解码

## 1. 接收端职责

接收端 B210 的两个射频通道同步连续采集同一频段，保存未经检测裁剪的原始 IQ。采集结束后，再分别运行前端检测、参数估计、单天线基线、MRC 和 SP-Decode。这样既保留可重复分析的数据，也避免实时处理来不及造成不可追溯的丢包。

## 2. 硬件布置

- 两根接收天线分别连接 B210 的通道 0 和通道 1，通常选择 `RX2`。
- 两天线位置、极化和间距在同一对比实验组中保持不变并拍照记录。
- 使用 USB 3.0，尽量把 IQ 写到本地 SSD。
- 控制端 B210 与接收端 B210 使用不同序列号，命令中明确指定。
- 当前 Fig. 9–12 正式 campaign 的双通道接收增益固定为 20 dB，正式组内不再改变。

## 4. 采集命令

30 s 单节点 run 建议采 50 s，使其覆盖控制帧、warmup、业务时段和尾部：

```bash
python3 capture_dual_b210.py \
  --out runs/run_01000101/run_01000101.sc16 \
  --run-id 0x01000101 \
  --duration 50 \
  --center-freq 487700000 \
  --rate 500000 \
  --gain 20 \
  --bandwidth 200000 \
  --channels 0,1 \
  --antenna RX2 \
  --device-args 'serial=RECEIVER_B210_SERIAL' \
  --notes 'Node01 single-node validation'
```

120 s 正式 run 建议采集时间至少覆盖：pre-config delay、CONFIG 重复阶段、pre-start delay、START ToA、warmup、duration 和 tail。按默认控制参数可先设 `--duration 145`。接收采集必须先启动，看到 `CAPTURE_ARMED` 后再启动控制端。

## 5. IQ 文件格式

输出 `.sc16` 是 sample-major、little-endian `int16`：

```text
ch0_I, ch0_Q, ch1_I, ch1_Q, ch0_I, ch0_Q, ch1_I, ch1_Q, ...
```

Python 读取示例：

```python
import numpy as np

raw = np.fromfile("run.sc16", dtype="<i2").reshape(-1, 2, 2)
iq = (raw[:, :, 0].astype(np.float32) +
      1j * raw[:, :, 1].astype(np.float32)) / 32768.0
ch0 = iq[:, 0]
ch1 = iq[:, 1]
```

同名 `.sc16.json` 记录实际硬件参数、每通道样点数、首个 USRP 时间戳、overflow、timeout、峰值、RMS 和 clipping。

## 6. 采集有效性检查

正式 run 必须满足：

```text
overflow_count == 0
timeout_count == 0
clipping_count == [0, 0]
samples_per_channel == round(duration_s * actual_rate_hz)
文件字节数 == samples_per_channel * 2通道 * I/Q两个分量 * 2字节
```

若 clipping 非零，降低接收增益后整轮重做。若 overflow 非零，优先检查 USB 3.0、磁盘写入速度、CPU 调度和虚拟机 USB 直通；不要在中间缺样点的 IQ 上做正式统计。

## 7. 前端从仿真叠加迁移到真实采集

原有仿真叠加前端不能直接假设“每个包的干净起点、发送节点或叠加系数已知”。真实采集至少要改为：

1. 输入由仿真数组改为上述双通道连续 IQ，并严格保留通道同步。
2. 在连续流上做噪声底估计、前导检测和候选帧聚类。
3. 每个候选分别估计起始时间、CFO、采样时钟偏差、幅度、相位和两通道复信道。
4. 允许同一窗口内有多个重叠候选，不能检测到第一个包后直接屏蔽整段。
5. 控制帧长度为 34/14 字节，业务帧固定为 20 字节；统计业务性能时过滤控制帧。
6. 检测器不得读取 manifest 中的期望发送时刻或真实节点 ID。
7. 为每个候选输出检测时间、置信度、两通道功率、CFO 和失败原因，方便定位前端瓶颈。

先在 N=1 的真实 IQ 上调通，再进入 N=2。N=1 都不能稳定检出和解码时，不应直接调 15 节点算法。

## 8. 后端必须锁定的配置

```text
SF=10
BW=125000
sample_rate=500000
coding_rate=4/5
preamble_len=8
explicit_header=true
phy_crc=true
sync_word=0x34
payload_len=20（数据帧）
```

双天线处理保留三条可比较路径：Ch0 单天线基线、Ch1 单天线基线、双通道 MRC/SP-Decode。所有路径使用同一批候选窗口和同一 CRC 判定，避免数据选择偏差。

## 9. payload 判定与去重

解码得到 20 字节后调用控制端共享代码：

```python
from protocol import decode_data_payload

packet = decode_data_payload(payload_bytes)
```

只有长度为 20、magic/version 正确、应用层 CRC16 正确、`run_id` 等于当前 run、`node_id` 属于 active_nodes 时才计为成功业务包。按 `(run_id, node_id, sequence)` 去重；同一包被多个窗口或算法路径解出时，有效载荷吞吐量只能计一次。正式 goodput 按 `唯一成功包数 × 20 × 8 / business_duration / 1000` 计算，单位为 kbps；PHY 头、前导和报告中的十六进制/JSON 字符不计入有效载荷。

## 10. 推荐结果表

每个候选至少输出：

```text
run_id, detector, decode_method, candidate_time_s, node_id, sequence,
phy_crc_ok, payload_crc_ok, duplicate, ch0_power_db, ch1_power_db,
cfo_hz, collision_order_est, failure_stage
```

每个 run 汇总：应发包估计数、检出候选数、PHY CRC 通过数、payload CRC 通过数、唯一成功包数、每节点成功数、吞吐量、PRR，以及 Ch0/Ch1/MRC/SP-Decode 的配对比较。
