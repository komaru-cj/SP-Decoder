# Fig. 9–12 自动采集命令（40 轮）

当前正式 campaign 为 `fig9_12_duty_v4`，共 40 轮。运行前必须确认15个节点均已烧录
扩展到16个 traffic profile 的新版固件：

- Fig. 9/10：`N={3,6,9,12,15}` × `d={0.05,0.15,0.25}` ×
  2 个独立 seed，共 30 轮；
- Fig. 11：使用已有干净包离线构造 2/4/6/8 包碰撞，不采集 USRP；解码时间排除
  检测/同步；所有方法共享 SP 包检测，LoRaWAN/MRC 共享 SP 精参数，其他方法从
  SP 粗起点运行论文内精估计，精估计失败记为 SER=1；
- Fig. 12：两节点间隔 `2/5/10/20/>20 cm`，固定 `d=0.25`，每个间隔做
  2 次真正的独立重复，共 10 轮；
- 只在第 1 轮结束后解码一次链路门；第 2–40 轮只采集，不逐轮解码。

> v3 通过虚假的“参考节点数”编码占空比，会被现有节点固件拒绝，已经废止。不要再运行
> `fig9_12_duty_v3` 中的脚本或 campaign。

Fig. 11 可在任意时刻独立运行：

```bash
cd /home/chengjing/real_usrp_experiment
env OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 MKL_NUM_THREADS=1 NUMEXPR_NUM_THREADS=1 \
python3 real_collision_experiment/paper_experiments/build_fig11_trace_runtime.py \
  --clean-packets real_usrp_outputs/clean_pos_packets.npz \
  --out-dir real_usrp_outputs/fig11_trace_runtime \
  --collision-orders 2,4,6,8 \
  --scenes-per-order 4 \
  --timing-repeats 3 \
  --max-offset-symbols 15 \
  --candidates-per-window 8 \
  --sp-sync-max-trials 32 \
  --stagger-high-order-preambles \
  --uniform-stagger-spacing-symbols 4.25 \
  --seed 20260801
```

两台电脑不需要联网或握手。两边读取相同的 `campaign.json`，每轮使用 240 秒固定时间槽。
Ubuntu 必须先启动，Windows 在 10 秒内启动。脚本自动选择 run_id、节点、seed、占空比
编码和等待时间，不需要手工改参数。

## 1. 第 1 轮：采集并做一次链路检查

节点全部摆好、上电，Ubuntu 接收端先执行：

```bash
cd /home/chengjing/real_usrp_experiment
bash real_collision_experiment/automation/start_offline_rx_preflight.sh
```

然后在 10 秒内，在 Windows PowerShell 执行：

```powershell
Set-ExecutionPolicy -Scope Process Bypass
& "C:\real_usrp_experiment\real_collision_experiment\automation\start_offline_control_preflight.ps1" `
  -PythonExecutable "D:\mysoft2\radioconda\python.exe" `
  -ControlTxGain 0
```

`-ControlTxGain` 是控制 B210 的发射增益；现场若已验证过其他值，把 `0` 换成该固定值。
节点数据包发射功率由 campaign 中的 `node_tx_power` 控制，与此参数不同。当前 40 轮
campaign 已固定为 **16 dBm**。Ubuntu 接收 B210 的两个通道增益已固定为
**20 dB**，无需在命令行另外传参。

第 1 轮也是正式 Fig. 9/10 数据：
`N=15, d=0.05, G=0.75`。Ubuntu 会采集 155 秒，扫描完整文件的
ADC clipping，并只解码 IQ 的 **20–50 秒**以跳过 CONFIG/START、覆盖低速率下每个
节点的首次发包机会并限制内存。前端能量预筛阈值固定为 `energy_min_ratio=3`。看到
`ONE_TIME_GATE_OK` 才能继续。若只有 gate 解码被 OOM/SIGKILL，不要重新发包，直接执行：

```bash
cd /home/chengjing/real_usrp_experiment
bash real_collision_experiment/automation/retry_offline_rx_gate.sh
```

## 2. 第 2–40 轮：自动连续采集

Ubuntu 接收端先执行：

```bash
cd /home/chengjing/real_usrp_experiment
bash real_collision_experiment/automation/start_offline_rx_remaining.sh
```

若 IQ 要写到另一块大容量磁盘：

```bash
cd /home/chengjing/real_usrp_experiment
RUNS_ROOT=/你的大容量磁盘/fig9_12_runs \
  bash real_collision_experiment/automation/start_offline_rx_remaining.sh
```

Ubuntu 通过磁盘检查并显示 `OFFLINE_RX_STARTED` 后，在 10 秒内运行 Windows：

```powershell
& "C:\real_usrp_experiment\real_collision_experiment\automation\start_offline_control_remaining.ps1" `
  -PythonExecutable "D:\mysoft2\radioconda\python.exe" `
  -ControlTxGain 0
```

第 2–30 轮为 Fig. 9/10。第 31–40 轮为 Fig. 12；在 sequence
`31、33、35、37、39` 前，两边会同步插入 300 秒换位时间并显示目标距离。依次把
Node02 相对 Node01 放到：

1. 2 cm；
2. 5 cm；
3. 10 cm；
4. 20 cm；
5. 大于 20 cm（当前 manifest 用 30 cm 代表）。

同一距离的两轮均为 `d=0.25, G=0.5`，但使用独立的 run_id 和 seed。换位时只移动 Node02，保持两节点相对
网关方位角、天线高度、极化和其他环境不变。

remaining 脚本遇到单轮控制或采集错误时会记录失败并继续下一个固定时间槽，最后生成
failure summary。不要临时手工补轮；全部结束后统一根据接收端、控制端和离线解码结果
生成双方一致的重跑清单。

## 3. 占空比如何编码

新版固件按真实活跃节点数计算 `d=G/N`。控制端自动使用：

| N | d=5% | d=15% | d=25% |
|---:|---:|---:|---:|
| 3 | G=0.15 | G=0.45 | G=0.75 |
| 6 | G=0.30 | G=0.90 | G=1.50 |
| 9 | G=0.45 | G=1.35 | G=2.25 |
| 12 | G=0.60 | G=1.80 | G=3.00 |
| 15 | G=0.75 | G=2.25 | G=3.75 |

`numActiveNodes` 永远等于 active mask 的置位数，控制端不再提供
`--traffic-reference-nodes`。固件修改约定见
`docs/11_节点固件扩展traffic_profile提示词.md`。

## 4. 时间与存储

- 每轮业务时长 120 秒，Ubuntu 实际采集 155 秒；
- 普通时间槽 240 秒；
- Fig. 12 有 5 次、每次 300 秒的换位时间；
- 40 轮从 preflight 到 remaining 分两次启动；
- 500 kS/s、双通道、complex int16 时，40 轮最终 IQ 约 23.1 GB
  （约 21.6 GiB），另需约 0.58 GiB 合并空间和默认 1 GiB 保留空间。

脚本启动时会按当前所选轮次精确检查剩余空间，并拒绝覆盖已有 run 目录或 manifest。

## 5. 实验结束后复制什么

从 Windows 完整复制：

```text
C:\real_usrp_experiment\real_collision_experiment\run_manifests\fig9_12_duty_v4_offline\
```

正常情况下应包含 40 个 `run_*.json`；如果控制端有失败，还会包含 failure summary。
Ubuntu 侧保留全部 `run_*/run_*.sc16` 和 `.sc16.json`。仅有 manifest 不能计算 PRR
或有效载荷吞吐量。

完整参数表在：

```text
real_collision_experiment/paper_experiments/generated/fig9_12_duty_v4/run_sheet.csv
```

后处理使用 `conditional_prr` 画 Fig. 9，并以成功解码的 20-byte payload 计算 Fig. 10
有效载荷吞吐量。确认属于硬件、控制或采集故障时，丢弃整次 attempt 并列入重跑清单；
不能因 PRR 低而删除数据，也不能只删除某节点或人为补 TPS。
