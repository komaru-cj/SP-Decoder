# 实验执行 SOP

## 1. 一次性准备

1. 给控制 B210、接收 B210、15 个节点分别贴唯一标签。
2. 记录两台 B210 序列号，避免控制与接收脚本选错设备。
3. 构建并保留 Node01 至 Node15 的 15 份 HEX。
4. 每块板烧录后立即贴对应标签，禁止依靠记忆区分。
5. 固定节点位置、接收天线位置、极化、供电方式和线缆。
6. 建立 run 目录，并把文档中的记录模板复制为本轮记录。

## 2. 每块板的单节点闭环验收

以 Node01 为例：

1. 只给 Node01 上电，其余 14 块断电。
2. 启动接收端 50 s 双通道采集。
3. 启动控制端：active-nodes=1、G=0.25、warmup=5 s、duration=30 s。
4. 观察 LED：初始灭，CONFIG 后常亮，START 后灭，随后出现发送闪烁。
5. 等采集结束，先检查 IQ JSON 无 overflow、timeout、clipping。
6. 运行前端和解码，确认 node_id=1、run_id 正确、sequence 递增、双 CRC 通过。
7. 记录两通道功率、CFO 和成功包数。
8. Node02 至 Node15 逐块重复；发现异常的板不进入正式实验。

单节点验收的目标不是比较算法，而是确认每个物理节点身份、射频链路和固件行为正确。

## 3. 两节点联调

1. 只给 Node01、Node02 上电。
2. 先做 N=2、G=0.5、30 s，确认两种 node_id 都能出现。
3. 再做 G=1.0 和 1.5，检查确实存在重叠帧，前端不会只保留强包。
4. 对比单天线与双天线结果，人工查看若干碰撞窗口的频谱/时频图。
5. 确认 manifest 未被检测器当作先验输入。

## 4. 四节点预实验

使用固定 Node01 至 Node04，依次做 G=0.5、1.0、1.5、2.0、3.0 的 30 s run。目标是暴露多候选检测、内存、计算时间、文件组织和统计脚本的问题。所有问题关闭后再接 15 块板。

## 5. 正式 15 节点单个 run 的严格顺序

1. 确认 15 块板均上电，PC13 初始为熄灭状态。
2. 在接收端创建本次 run 目录，写入唯一 run_id。
3. 启动接收脚本，看到 `CAPTURE_ARMED`。
4. 启动控制脚本。不要反过来，否则可能漏掉 CONFIG/START 和最早业务包。
5. CONFIG 阶段抽查 LED 应常亮；START 后应熄灭。
6. 业务阶段不要移动节点、天线、线缆或改变增益。
7. 等到控制 manifest 中 `expected_capture_end_utc` 之后再停止采集；若采集脚本已指定固定时长，让它自然结束。
8. 立即保存控制终端输出、接收终端输出和现场记录。
9. 先跑数据完整性门槛；失败则标记 invalid 并重做，不进入解码统计。
10. 运行前端和各解码路径，生成逐包结果与 run 汇总。
11. 检查 15 个节点是否都有观测包；缺失节点先查单节点基线与 LED 录像。

## 6. 推荐目录结构

```text

  run_0f020101/

    control_console.txt
    run_0f020101.sc16
    run_0f020101.sc16.json
    receiver_console.txt

```

控制 manifest 原文件可以保存在控制机，同时复制到对应 run 目录。复制后校验文件大小或 hash，避免传错 run。

## 7. 无 USB-TTL 时的对账方法

1. manifest 给出每个节点按固件算法计算的期望发送序列。
2. payload 给出实际被正确解出的 node_id 和 sequence。
3. 对每个节点计算：期望序号集合、成功序号集合和未观测集合。
4. “未观测”可能是节点未发、空口深衰落、检测漏包或解码失败；没有额外节点日志时不能进一步作唯一归因。
5. 若某节点整轮为零，先单独重测该板；若单节点正常，再检查正式 run 的 CONFIG/START 接收和 near-far 情况。

论文统计时建议同时给出：相对“固件期望调度”的端到端 PRR，以及相对“前端检出候选”的后端成功率。两者含义不同，不能混为一个指标。

## 8. 快速故障树

| 现象 | 首要检查 |
|---|---|
| 所有节点都不进入 CONFIG 常亮 | 控制 B210 设备、TX 天线口、487.7 MHz、sync 0x34、LoRa 参数 |
| CONFIG 常亮但 START 后不灭 | START 的 run_id/CONFIG CRC、控制脚本是否完成发送 |
| LED 有发送闪烁但 IQ 没信号 | 接收 B210 序列号、RX2、中心频率、天线、增益 |
| IQ 有强信号但全解码失败 | SF/BW/CR/header/CRC/sync/sample rate 配置 |
| 只有近端节点成功 | near-far、接收过载、节点功率差、信道估计和 SIC 顺序 |
| overflow > 0 | USB 3.0 直通、SSD、宿主机负载、虚拟机资源 |
| clipping > 0 | 降低接收增益，整轮重采 |
| 节点 ID 与贴纸不符 | 烧错 HEX，重新构建并烧录正确 NodeXX |

## 9. 从现在开始的最短路径

1. 完成 Node01 的 N=1 闭环：控制、LED、双通道 IQ、解码、payload CRC。
2. 同样验收 Node02 至 Node15。
3. 完成 Node01+Node02 的真实碰撞联调。
4. 将 VMware 中前端/后端源码接入 `.sc16` 读取和真实连续流检测。
5. 通过四节点预实验后，才开始 15 节点正式矩阵。
