# 控制端：Ubuntu + USRP B210

## 1. 职责

控制端不发送实验数据包，只发送两类 LoRa 控制帧：

1. `CONFIG`：声明 run、活动节点集合、`N`、`G`、节点功率、时长、warmup 和随机种子。
2. `START`：携带相同 `run_id` 和 CONFIG CRC，通知已经接收配置的节点同时开始。

控制端发送 5 次 CONFIG，再发送 1 次 START。节点接收任意一次合法 CONFIG 即进入等待 START 状态；重复 CONFIG 可以提高可靠性。

## 2. 软件准备

Ubuntu 上需要 UHD、GNU Radio 3.10 和已安装的 `gr-lora_sdr`：

```bash
uhd_find_devices
python3 -c "import uhd; import gnuradio; import lora_sdr; print('environment OK')"
cd /path/to/LoRa_workStation-main/real_collision_experiment/control_usrp
python3 -m unittest -v
```

把控制 B210 的 TX/RX 口接天线。首次实验从较低增益开始，例如 `--usrp-tx-gain 0`；控制端与节点距离很近时不要盲目加大增益。

## 3. 控制协议

所有多字节整数均为 little-endian，CRC 为 CRC-16/CCITT-FALSE 风格参数：初值 `0xFFFF`、多项式 `0x1021`、不反射、无最终异或。

### CONFIG，34 字节

| 偏移 | 长度 | 字段 |
|---:|---:|---|
| 0 | 2 | magic = `SP` |
| 2 | 1 | version = 1 |
| 3 | 1 | type = 1 |
| 4 | 1 | frame_size = 34 |
| 5 | 1 | flags |
| 6 | 4 | run_id |
| 10 | 2 | active_mask，bit0 对应 Node01 |
| 12 | 1 | num_active_nodes |
| 13 | 1 | phy_profile_id，当前只能为 0 |
| 14 | 1 | traffic_profile_id |
| 15 | 1 | node_tx_power_dbm，int8 |
| 16 | 4 | duration_ms |
| 20 | 4 | warmup_ms |
| 24 | 4 | global_seed |
| 28 | 4 | payload_seed |
| 32 | 2 | frame_crc16 |

### START，14 字节

| 偏移 | 长度 | 字段 |
|---:|---:|---|
| 0 | 2 | magic = `SP` |
| 2 | 1 | version = 1 |
| 3 | 1 | type = 2 |
| 4 | 1 | frame_size = 14 |
| 5 | 1 | flags |
| 6 | 4 | run_id |
| 10 | 2 | CONFIG 帧 CRC |
| 12 | 2 | START 帧 CRC16 |

START 只有在 `run_id` 和 CONFIG CRC 都与节点当前缓存配置匹配时才会被接受，旧 run 的 START 不会误启动新实验。

## 4. G 如何控制

命令行直接使用 `--offered-load`：

```text
0.25 -> profile 0
0.5  -> profile 1
1.0  -> profile 2
1.5  -> profile 3
2.0  -> profile 4
3.0  -> profile 5
```

程序将 profile 和 `N` 写入 CONFIG；每个节点用相同公式和不同种子独立生成指数间隔。因此控制 B210 可以控制整场实验的 G，但不会逐包遥控某个节点在某一时刻发送。

## 5. 先做 dry-run

dry-run 不访问 B210，只生成和检查 manifest：

```bash
python3 usrp_run_controller.py \
  --run-id 0x01000101 \
  --active-nodes 1 \
  --offered-load 0.25 \
  --duration-s 30 \
  --warmup-s 5 \
  --node-tx-power 2 \
  --manifest-dir runs/manifests \
  --dry-run
```

检查 JSON 中的 `active_mask`、`num_active_nodes`、`offered_load`、`duration_ms`、两个 seed 和控制帧 hex。

## 6. 单节点正式控制命令

```bash
python3 usrp_run_controller.py \
  --run-id 0x01000101 \
  --active-nodes 1 \
  --offered-load 0.25 \
  --duration-s 30 \
  --warmup-s 5 \
  --node-tx-power 2 \
  --config-repeat 5 \
  --config-interval-s 1 \
  --pre-config-delay-s 5 \
  --pre-start-delay-s 3 \
  --tail-s 3 \
  --device-args 'serial=CONTROL_B210_SERIAL' \
  --usrp-tx-gain 0 \
  --antenna TX/RX \
  --manifest-dir runs/manifests
```

## 7. 15 节点正式控制命令

```bash
python3 usrp_run_controller.py \
  --run-id 0x0F020101 \
  --active-nodes 1-15 \
  --offered-load 1.0 \
  --duration-s 120 \
  --warmup-s 5 \
  --node-tx-power 2 \
  --config-repeat 5 \
  --config-interval-s 1 \
  --pre-config-delay-s 5 \
  --pre-start-delay-s 3 \
  --tail-s 5 \
  --device-args 'serial=CONTROL_B210_SERIAL' \
  --usrp-tx-gain 0 \
  --manifest-dir runs/manifests
```

替换序列号和 run_id。`--active-nodes 1-15` 也可以写成 `1,2,3,...,15`。

## 8. Manifest 说明

`run_manifests/run_XXXXXXXX.json` 包含：

- 完整 run 配置和控制帧十六进制。
- 理论 ToA、理论平均 gap、固件整数平均 gap。
- 每个活动节点的期望发送起始时间列表。
- CONFIG 和 START 入队的 UTC 时间。
- 预计接收采集结束时间。

`expected_node_schedules` 精确复现固件的 xorshift32 和 Q16 指数间隔算法，但节点晶振误差、启动延迟、TX timeout 或复位都会使实际空口时刻偏离。它只能用于事后核对，不能喂给检测器。

## 9. 控制成功的现场判断

没有 USB-TTL 时观察节点 PC13 LED：

- 上电后熄灭：等待 CONFIG。
- CONFIG 被接受后常亮：等待 START。
- START 后熄灭：warmup 或等待随机发送。
- 业务期间约 371 ms 的亮脉冲：正在发送数据包。

若 LED 从未常亮，优先检查控制端频率、sync word、CRC、天线口和增益。若常亮后一直不灭，说明 START 没有被接受，检查 run_id/CONFIG CRC 或重新发送整个 run。

## 10. 常见错误

| 现象 | 处理 |
|---|---|
| `No module named lora_sdr` | 重新安装 OOT 模块，并确认控制脚本使用同一个 Python 环境 |
| `No devices found` | 检查 USB 3.0、权限、序列号和 `uhd_find_devices` |
| CONFIG 间隔报错 | 34 字节 SF10 控制帧 ToA 较长，保持默认 1 s 间隔 |
| 单节点选择 G=1 或更大 | 单节点要求 `G < N`，改为 0.25 或 0.5 |
| 节点偶尔漏配置 | 保持至少 5 次 CONFIG，适当改善天线/距离，不能只重复 START |
