# 十五节点真实碰撞全流程

## 先做的三件事

1. 给 15 块 F103 分别编译并烧录 `EXPERIMENT_NODE_ID=1..15`，贴实体标签，保存每块板的上电 `BOOT` 日志。
2. 用单节点分别发送短 run，测每个节点在两根接收天线上的 RSSI、CFO、包数和 CRC，通过摆位或节点功率把强弱差控制到计划范围。
3. 先验证控制帧兼容性：所有节点应连续打印相同 `CONFIG_OK` 和 `START_OK`，且 run_id/config CRC 一致。未完成这一步不要直接开十五节点长实验。

## 推荐递进矩阵

| 阶段 | 活跃节点 | G | 目的 |
| --- | --- | --- | --- |
| A | 每次 1 个，共 15 个 | 0.25 | 单节点基线、位置/功率/CFO 清单 |
| B | 选定 2 个 | 0.5、1.0 | 验证真实双包重叠和标签匹配 |
| C | 4 个 | 0.5、1.0、2.0 | 检查检测器在多候选下的稳定性 |
| D | 15 个 | 0.25、0.5、1、1.5、2、3 | 论文主实验 |

每个条件至少使用不同 seed 重复 5 次。先用 30 秒短 run 排错，再用 120 秒或计划规定时长采正式数据。run_id 不能复用。

## 单次运行顺序

1. 节点全部上电，确认都处于 `WAIT_CONFIG`，开始保存 15 路 UART 日志。
2. 接收 B210 设置双通道、1 MS/s、487.7 MHz、固定增益、同一时钟源，先采 3 到 5 秒纯噪声用于校准。
3. 启动接收端连续 IQ 写盘，保存 `sc16` 数据、首样点时间、中心频率、采样率、增益、天线编号和所有 overflow 事件。
4. 在控制 Ubuntu 运行 `usrp_run_controller.py`。核对它生成的 manifest 与接收端目录使用相同 run_id。
5. 从 UART 观察所有活跃节点均收到 CONFIG/START；若有节点缺失，整次 run 标记失败，不在中途补发 START。
6. 采集持续到 manifest 的 `expected_capture_end_utc` 之后至少 2 秒，再停止 IQ 和串口日志。
7. 首先做完整性门禁，再启动耗时解码：文件长度正确、无 overflow、15 路日志齐全、活跃节点都有 `RUN_COMPLETE`、manifest CRC 一致。

## 最小闭环验收

1. 单节点：接收端应用 CRC 通过率接近 100%，解出的 node/sequence 与 UART 连续一致。
2. 双节点：从 IQ 时频图能看到真实重叠；检测器能输出两个候选；MRC 和 SP-Decode 均使用估计参数运行。
3. 四节点：改变 seed 后观测到碰撞比例随 G 单调增加，接收包数与节点 UART 发包总数在统计上吻合。
4. 十五节点：每个条件输出检测召回、PHY CRC 成功率、应用 CRC 成功率、PER/SER、按 SIR/方向相关性分层的 MRC 与 SP-Decode 对比。

控制 B210 与接收 B210 不需要共享采样时钟；控制帧本身会出现在接收 IQ 中，可作为 run 起点标记。但接收 B210 的两个 RX 通道必须保持同机同步，且控制发射天线应与接收前端保持足够隔离，防止 START/CONFIG 使 ADC 饱和。所有射频发射应在获得许可的频段和屏蔽/合规条件下进行。
